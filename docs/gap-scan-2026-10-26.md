## Filed backlog

All four cards were created with product `yebomart`, status `backlog`, priority `high`, type `bug`, label `gap-scan`. Ordering prioritizes inventory integrity, then missing financial effects. The descriptions below are the filed implementation contracts, not claims that fixes are shipped.

### 1. Make return restocking preserve concurrent inventory changes

Dashboard ID: `task-1793020960022-p6684n`. Components: yebomart-api.

Evidence: src/controllers/return.controller.ts process complete reads Product.quantity then assigns quantity = previousQty + returned quantity (lines 435-452). It locks Sale/Return, not Product before reading. Two different returns, a sale, or a restock can interleave and overwrite committed units. Example: stock 10, return +2 reads 10, sale -3 commits 7, return assigns 12 instead of 9. Existing stock task 1792573369483 fixed StockService only; return entitlement task 1792447323832 prevents over-returning a sale but does not serialize product mutations across different sales.
Definition of done: use transaction-scoped product locks/atomic deltas for return restocks and the adjacent exchange writes, with consistent product lock ordering and accurate StockLog previousQty/newQty. Reuse current StockService/SaleService patterns without adding compatibility paths or duplicating inventory logic. Preserve entitlement locks, shop validation, trackStock handling and all-or-nothing completion. Add coordinated real Postgres regressions using integration/lockedRace.ts for return versus sale, return versus restock and two different returns touching one product. Verify final inventory equals all signed movements and logs form a consistent chain; failures roll back status, restocked flags, stock and logs. The cancelled exchange-negative-stock card task-1782242520958-sn51ae is related history, not an active duplicate; preserve any existing guards while making exchange writes concurrent-safe.

### 2. Post completed store-credit returns to the customer ledger

Dashboard ID: `task-1793020960214-g14tq6`. Components: yebomart-api + yebomart-app.

Evidence: app/src/pages/Returns.tsx offers Store Credit and submits STORE_CREDIT with an optional customer. api/src/controllers/return.controller.ts create stores refundAmount=0 for this type (line 181); process complete only mutates stock and status, never CustomerCredit or Customer.balance. prisma/schema.prisma describes STORE_CREDIT as credit to customer account. A completed 50-value return can remove the goods from the customer without giving any account credit.
Definition of done: require and validate a recipient in the active shop for STORE_CREDIT, persist or deterministically derive its authoritative entitlement value, and apply exactly one signed account-credit entry in the same transaction as completion. Reuse applyCustomerCredit and the existing positive-debt/negative-credit convention; link the entry to the return so retries are auditable and cannot double-credit. Surface credited amount/customer in return details and customer statement. Do not create a second wallet or add compatibility behavior. Cover paid-sale full/partial returns with VAT/discount allocation, missing/foreign customer, retries, competing completions, concurrent ledger writes, and injected ledger failure proving rollback. Keep CREDIT-sale debt settlement distinct (separate task) and define validation to prevent double benefit. No success toast without a persisted ledger effect.

### 3. Reverse the returned portion of customer debt on pay-later sale returns

Dashboard ID: `task-1793020960423-0jeibb`. Components: yebomart-api + yebomart-app.

Evidence: SaleService.create posts CustomerCredit PURCHASE for CREDIT sales and voidSale reverses booked debt, but ReturnController.process never reads or mutates that ledger. Returning items worth 40 from an unpaid 100 CREDIT sale leaves the customer owing 100 even after completion. create validates customerId only by shop and does not bind the return recipient to the original credit-sale debtor. Existing done task-1792447324000-ruidw6 covers voiding, not partial returns.
Definition of done: settle eligible CREDIT-sale returns against the original booked debt, deriving value from existing sale entitlement and linking exactly one reversal to each completed return. Reuse customerCredit locking/ledger rules and coordinate with STORE_CREDIT return work; prevent duplicate debt reduction/account credit or a cash refund of an unpaid amount. Verify original debtor identity, preserve repayments, and define explicit supported handling for fully/partly repaid sales; reject ambiguous histories clearly rather than guessing. App must explain the account adjustment and reject unsupported refund choices before showing success. Add real Postgres tests for partial/full returns, repayment-before-return, concurrent return/payment and competing completions, foreign customer, and rollback. Customer.balance must equal signed ledger sum and original repayments must remain intact. No backward compatibility shims or direct-provider payment integration.

### 4. Include recorded cash refunds in till cash-up and Z reports

Dashboard ID: `task-1793020960613-91ak4n`. Components: yebomart-api + yebomart-app.

Evidence: CashSessionService.cashSalesTotal aggregates only COMPLETED CASH sales; getCurrent/close compute expectedCash = openingFloat + cashSalesTotal. ReturnController completion has no refund tender or cash-session attribution and zReport also queries only Sale. With float 100, cash sale 50, and cash refund 20 paid from the drawer, counted cash 130 is incorrectly compared to 150 (variance -20). The original sale remains COMPLETED. Existing Z-report discount and concurrent till-transition tasks do not cover cash outflows.
Definition of done: record actual refund settlement method and attributable till/session when a cash refund is confirmed, atomically with return completion, and deduct confirmed cash outflows exactly once in live expected cash, close variance and printed/on-screen Z report. Separate merchandise return approval from proof of money paid; never assume every REFUND is cash or a provider refund succeeded. Reuse existing till/return models and settlement code where possible. Clearly reject unsupported/no-open-till cash payout flows; define current-session attribution for refunds of prior-session sales. Add tests for the 100+50-20=130 example, prior-day sale refunded today, noncash and store-credit returns excluded from cash outflows, pending/rejected returns, retries, concurrent close/refund, shop isolation and transaction rollback. Preserve existing gross/discount/VAT semantics and immutable closed-session figures. Coordinate with CREDIT-sale debt settlement; no invented cash payout on unpaid credit.

## Boundaries and follow-up

- Stock race work concerns different operations touching Product rows. Existing return entitlement/duplicate completion locks only serialize the original Sale/Return, and do not close this race.
- Store-credit posting and pay-later reversal must share return settlement identity/locking. They must not independently credit the same value twice. Implement unpaid-credit validation alongside store credit, or reject that combination clearly until debt settlement is ready.
- Cash refund work concerns actual drawer movements and session attribution. Provider refunds must use existing YeboPay integration where supported; a return status is not evidence of a successful payout.
- Sales/profit reports also aggregate completed sales without return adjustments (`src/services/report.service.ts`). Deferred from this batch until refund/account settlement semantics are authoritative, to avoid a parallel financial model.
- Exchange UI/value settlement needs further investigation; it was not filed as a speculative additional feature. The cancelled exchange-negative-stock card is historical context for the inventory task, not an active duplicate.
